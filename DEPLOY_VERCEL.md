# FastAPI на Vercel и Postgres на Neon

Деплой выполняется вручную владельцем проекта. Код JSON API не меняется;
авторизованные вызовы получают прежние тела ответов. База SQLite и её данные
не переносятся в Neon автоматически.

## Точка входа и настройки Vercel

- Root Directory: корень этого репозитория; приложение — **`main:app`**.
- Vercel обнаруживает экспорт `app` из корневого `main.py`. Node-сервер и фронт
  отдельно не собираются; rewrite на другой хост здесь не нужен.
- `vercel.json` настраивает функцию `main.py` и `maxDuration:60`. Синхронная
  оценка/батч должны укладываться в это время. Долгие батчи требуют отдельного
  работника/очереди; этот API пока остаётся синхронным. Полный DEV-батч с реальной
  моделью не был запущен для этой проверки.
- `.vercelignore` исключает локальные БД, окружения, секретные файлы, тесты и
  исходный архив. `prompts`, `checklists` и Python-код остаются в пакете.
- При `VERCEL` приложение требует Postgres, `FRONTEND_ORIGIN` и длинный
  `API_AUTH_TOKEN`. Без них запуск завершается ошибкой, а не переключается на SQLite.
- При старте Postgres проверяется версия схемы; DDL и seed на cold start **не запускаются**.

[Официальная документация Vercel](https://vercel.com/docs/frameworks/backend/fastapi).

## Подключение и миграции

Для приложения используйте выданную Neon pooled-строку в `DATABASE_URL` с её
SSL-настройками. Для миграций можно отдельно задать direct-строку в
`DATABASE_MIGRATION_URL`; если её нет, команда использует `DATABASE_URL`.
Строки не передаются в аргументах CLI и не печатаются кодом миграций.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m backend.migrate_postgres
```

Команда идемпотентна: DDL и отметка версии сохраняются одной транзакцией,
параллельные миграции защищены транзакционной блокировкой. Схема Postgres
находится в `backend/migrations/postgres`; SQLite использует свои прежние миграции.

Только для отдельной тестовой БД можно добавить синтетические данные:

```powershell
.\.venv\Scripts\python.exe -m backend.migrate_postgres --seed-demo
```

Не запускайте тестовый seed на рабочей Neon-БД. Рабочие диалоги загружаются через
`POST /api/groups/{gid}/load`. Для каналов группы должны быть настроены активные
чек-листы; seed содержит только чат, версии звонков добавляются через API чек-листов.

Драйвер — psycopg 3, подготовленные запросы отключены для совместимости с pooler.
Каждая операция открывает и закрывает соединение. Чтение связанных данных использует
согласованный снимок, записи — транзакции; распределённая блокировка защищает
нумерацию версий и конфликты апелляций между экземплярами функций.
Миграционной роли нужны права DDL; роли приложения — CRUD таблиц,
чтение `schema_migrations` и USAGE последовательностей.

[Подключение Neon](https://neon.com/docs/connect/connect-from-any-app),
[ограничения pooler](https://neon.com/docs/connect/connection-pooling).

## CORS и доступ

`FRONTEND_ORIGIN` — один точный origin фронта: схема, хост и при необходимости порт,
без пути, завершающего `/` и `*`. В CORS разрешены `GET`, `POST` и заголовки
`Content-Type`, `Authorization`. Поддомены и preview-адреса автоматически не разрешаются.
Preflight не требует токена; API-ответ 401 также получает CORS-заголовок для разрешённого origin.

Все `/api/*`, включая диалоги, импорт, одиночную/пакетную оценку и изменения данных,
при заданном `API_AUTH_TOKEN` требуют заголовок `Authorization: Bearer …`.
На Vercel токен обязателен и должен быть случайным, не короче 32 символов.
Локально без этого параметра прежний API остаётся доступным без авторизации.
`/health` остаётся публичным и не отдаёт диалоги или секреты.

Это общий сервисный токен, не система пользователей и ролей. Нет встроенных квот,
ограничения расходов модели или распределённого rate limit. `LLM_CONCURRENCY`
ограничивает параллелизм одного батча, а не всех запросов приложения.
CORS не заменяет авторизацию. Не встраивайте токен, ключ модели и строки БД в
публичный JS-бандл; для общего публичного фронта нужен BFF/пользовательская авторизация.

Базовый URL после деплоя — публичный HTTPS origin функции. Маршруты уже содержат
`/api`, поэтому этот префикс не нужно добавлять дважды.

## Локальный SQLite

Уберите `DATABASE_URL` из окружения локального процесса. Тогда используется
`CQA_DATABASE_PATH` либо `data/cqa.sqlite3`; SQLite по-прежнему мигрирует при старте.

```powershell
Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe -m backend.database --seed-demo
.\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

## Проверки

Интеграционные тесты используют **только** `TEST_DATABASE_URL`, не рабочий `DATABASE_URL`.
Они создают случайную схему `cqa_test_…` и удаляют только её после теста. Внешний API
и модель подменены. Проверяются повторный импорт, оценка и её критерии, новая версия,
апелляция с исходным/финальным итогом, параллельное выделение версий и откат оценки.

```powershell
$env:PYTHONUTF8 = "1"
Push-Location backend
try {
    & ..\.venv\Scripts\python.exe -m pytest -q tests/test_postgres_integration.py
} finally {
    Pop-Location
}
```

Без `TEST_DATABASE_URL` эти три теста явно пропускаются; это не подтверждение Postgres.
Локальные секреты можно держать в `.tmp/deploy-test.env` или окружении PowerShell;
приложение автоматически `.env`-файлы не читает. Вводите секреты через `Read-Host
-AsSecureString` или менеджер секретов, не вставляйте значения в чат/логи.

## Имена переменных окружения

Обязательные для Vercel: `DATABASE_URL`, `FRONTEND_ORIGIN`, `API_AUTH_TOKEN`.
Для реальной модели: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`.
Для импорта: `CQA_API_URL`.
Дополнительные настройки: `LLM_CONCURRENCY`, `LLM_VOTES`, `LLM_TEMPERATURE`,
`LLM_JSON_MODE`, `LLM_PRICE_IN`, `LLM_PRICE_OUT`.
Для миграций: `DATABASE_MIGRATION_URL` (необязательно).
Для тестов: `TEST_DATABASE_URL`.
Только локальный SQLite: `CQA_DATABASE_PATH`.
`VERCEL` задаётся самой платформой.
