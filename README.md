# CQA · backend (ветка `backend`, FastAPI)

Серверная часть: `main.py` (`main:app`), маршруты в `backend/`, оценщик `backend/cqa/`, миграции SQLite и Postgres,
тесты `backend/tests/`. Общая инструкция — запуск всей системы, подключение фронта, проверка, финальная группа — в
[главном README (ветка main)](https://github.com/Wigunilmi/data-challenge-bioc-team/blob/main/README.md).
Задеплоенный API: `https://data-challenge-bioc-team.vercel.app` (публичны `/health` и `/docs`, `/api/*` — по Bearer-токену).

## Быстрый старт (macOS / Linux, из корня ветки)

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000   # SQLite data/cqa.sqlite3, без токена, MOCK без LLM_API_KEY
curl http://127.0.0.1:8000/health                                           # {"status":"ok"}; Swagger: http://127.0.0.1:8000/docs
cd backend && PYTHONUTF8=1 ../.venv/bin/python -m pytest -q                 # тесты
```

Для загрузки групп задайте `CQA_API_URL` (GET-ссылка организаторов без `group_id`); чек-листы чатов и звонков в чистую
базу добавляет `node tools/seed-backend.mjs http://127.0.0.1:8000` из ветки `frontend`. Команды для Windows PowerShell — ниже.
Переменные окружения перечислены в [DEPLOY_VERCEL.md](./DEPLOY_VERCEL.md#имена-переменных-окружения).

## Vercel и Neon

[Инструкция деплоя FastAPI и миграций Postgres](./DEPLOY_VERCEL.md).
`DATABASE_URL` выбирает PostgreSQL; без него локальный запуск использует прежний
SQLite. На Vercel SQLite запрещён, миграции Postgres запускаются отдельной командой
`python -m backend.migrate_postgres`, а не при старте функции.
`FRONTEND_ORIGIN` задаёт точный CORS origin; `API_AUTH_TOKEN` защищает все `/api/*`
через Bearer-заголовок. На Vercel оба параметра обязательны. Локально без токена
API сохраняет прежний доступ. Ключи, токены и строки подключения не печатаются.

Требуется Python 3.10 или новее. Выполняйте команды из папки проекта в Windows PowerShell.

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Запуск сервера:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

Проверка в другом окне PowerShell:

```powershell
$response = Invoke-WebRequest -Uri "http://127.0.0.1:8000/health" -UseBasicParsing
```

Синтетический диалог не использует датасет организаторов.

В другом окне:

```powershell

    -ContentType "application/json" -Body '{"conversation_id":"synthetic-chat-001"}'
```

Успешный ответ — `200` и `View` по контракту. Активный чек-лист выбирается по каналу
до вызова модели; оценка и все результаты сохраняются одной транзакцией вместе с
`checklist_id` и `checklist_version`. Итоги вычисляются при формировании ответа и
в БД не сохраняются. Для неизвестного ID ответ — `404` и

Они запускаются той же командой `python -m pytest -q` из `backend` (см. ниже).
После добавления маршрута: **489 passed in 5.93s**, включая 480 прежних тестов и
9 новых. Отдельный тест запускает настоящий `evaluate` с подменой транспорта
модели; настоящий ключ и внешние сервисы не используются. Starlette выдаёт одно

## Апелляции

- `POST /api/appeals` принимает `{evaluation_id, criterion_id, comment, author?}`
  и возвращает апелляцию со статусом `open`. Комментарий обязателен, пробелы по
  краям удаляются; автор по умолчанию — `Оператор`.
- `GET /api/appeals?status=open|upheld|changed` возвращает апелляции от новых к
  старым, каждую с `conversation_id`. Без фильтра возвращаются все апелляции.
- `POST /api/appeals/{id}/decide` принимает `{action, reason, answer?|score?|na?}`
  и возвращает `{appeal, evaluation}`. Причина обязательна; `reviewer` можно задать
  дополнительно (по умолчанию `Проверяющий`).

`action:change` сохраняет статус `changed` и поправку `decision.result` к критерию.
`action:uphold` подтверждает исходную оценку, то есть отклоняет апелляцию: статус
`upheld`, причина и проверяющий сохраняются, результат критерия не меняется.
Снимок исходного результата хранится в `original`; решение содержит `reason`,
`reviewer`, `decided_at` и, только для изменения, `result`.

Миграция `backend/migrations/003_appeals.sql` добавляет таблицу апелляций и
ограничение одной открытой апелляции на пару оценка/критерий. Повторная открытая
апелляция или повторное решение дают `409`; неизвестная оценка/апелляция — `404`,
неизвестный критерий или пустой комментарий/причина — `400`. Создание и решение
сохраняются транзакционно, включая защиту от параллельных запросов.

Оригинальные результаты `results` не перезаписываются. При каждом чтении
`final_results` собираются из них и сохранённых решений; `totals` и
`original_totals` считаются по версии чек-листа, закреплённой за оценкой.
Числовые итоги не сохраняются в БД. Как в эталонном `view()`, если для критерия
существует несколько апелляций со статусом `changed`, применяется первая в порядке
создания. Список диалогов возвращает финальный `total`, исходный `original_total`
и счётчики апелляций последней оценки. История карточки также учитывает решения
соответствующих оценок. Модель при работе с апелляциями не вызывается.

## Пакетная оценка

`POST /api/evaluate-batch` принимает `{group_id?, only_missing?, concurrency?}` и
возвращает `{count, ms, cost_usd, results}`. При указанном `group_id` обрабатывается
вся группа; без него — все загруженные диалоги, без ограничения числа записей.

В начале запроса одним снимком БД фиксируются диалоги и активные наборы/версии
чек-листов по каналам. Последующая активация другой версии не меняет уже запущенный
батч. Используется тот же код оценки и сохранения, что в `POST /api/evaluate`.

Параллелизм: `concurrency` из тела запроса, иначе `LLM_CONCURRENCY` из окружения
FastAPI, иначе **4**. Значение должно быть положительным целым числом. Лимит
ограничивает число одновременно выполняемых оценок диалогов; очередь не создаёт
отдельную задачу на каждый диалог сразу.

По умолчанию `only_missing=false`: каждый запуск создаёт новые оценки.
При `only_missing=true` пропускаются диалоги, у которых уже есть завершённая оценка
выбранных `checklist_id` и `checklist_version`, включая результат с `total:null`.
Если такая оценка есть в истории, более поздняя оценка другой версии не мешает её
учесть. После активации новой версии прежние оценки сохраняются, а диалоги без
оценки новой версии обрабатываются заново.

Каждый диалог сохраняется отдельной транзакцией. Ошибка модели или БД у одного
диалога не отменяет остальные: HTTP-ответ батча — `200`, а соответствующий элемент
имеет `{ok:false,cid,error}`. Успешный элемент — `{ok:true,cid,total,cost_usd}`.
Результаты идут в исходном порядке; `count` — число выбранных попыток, включая
неуспешные. Верхний `cost_usd` суммирует успешные оценки и округляется до 4 знаков.
Пустой или полностью пропущенный батч возвращает `count:0` и `results:[]`.

Пример тела запроса: `{"group_id":"DEV","only_missing":true}`.
Настройка PowerShell перед запуском сервера: `$env:LLM_CONCURRENCY = "4"`.
Тесты `backend/tests/test_api_batch.py` используют только подмену модели и временные
БД с 14 синтетическими диалогами; реальный DEV и реальная модель для батча не вызывались.

## Чек-листы и версии

В текущем `API_CONTRACT.md` используются маршруты во множественном числе:

- `GET /api/checklists` — наборы с `id`, `name`, `channels`, `active`, `versions`
  и `active_checklist`.
- `POST /api/checklists` с `{name, channels, checklist, note?}` — новый набор,
  ответ `{id}`. Указанные каналы переходят новому набору; каждый канал принадлежит
  только одному набору.
- `POST /api/checklists/{id}/versions` с `{checklist, note}` — проверка критериев,
  новая версия и её активация для всех каналов набора, ответ `{version}`.
- `POST /api/checklists/{id}/activate` с `{version?}` и/или `{channels?}` — выбор
  сохранённой версии и/или привязка каналов, ответ `{ok:true}`.

Маршруты `/api/checklist` в единственном числе в контракте отсутствуют и не добавлены.
Изменение критерия передаётся как полный JSON чек-листа в маршрут `/versions`.
Старая версия и оценки не перезаписываются. Номер следующей версии и переключение
активности сохраняются одной транзакцией; параллельные изменения получают разные номера.

Миграция `backend/migrations/002_checklist_metadata.sql` сохраняет существующую
таблицу `checklist_versions` и добавляет метаданные версий и активного набора.
Она применяется автоматически при старте либо командой
`.\.venv\Scripts\python.exe -m backend.database`. Для старых версий без записанного
времени создания `created_at` возвращается как `null`; у новых версий — UTC ISO timestamp.

Новая версия активируется сразу при создании через `/versions`, как указано в
контракте (`validate, append, make active`). Отдельный `/activate` нужен для выбора
существующей версии и/или изменения привязки каналов.
При смене активной версии прежний итог в карточке и истории остаётся рассчитанным
по версии оценки. Поле `outdated` есть только в строке списка: `true`, если
сохранённая оценка относится к другому набору или версии. Карточка содержит ровно
`conversation`, `evaluation` и `history`, без дополнительного поля `outdated`.
Это чтение не обращается к модели.

## Список и карточка диалога

`GET /api/conversations` возвращает строки списка по контракту; `?group=DEV`
оставляет только диалоги указанной группы. У диалога без оценки `total`,
`original_total`, модель и версия чек-листа равны `null`.

`GET /api/conversations/{id}` возвращает `conversation`, последнюю сохранённую
оценку `evaluation` (или `null`) и `history` от старых оценок к новым.
Неизвестный ID: `404` с `{"error":"not found"}`.

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/api/conversations?group=DEV"
Invoke-RestMethod "http://127.0.0.1:8000/api/conversations/p1-en-001"
```

GET не вызывает модель и не создаёт оценки. Итоги списка, карточки и каждой записи
истории пересчитываются из сохранённых критериев по `checklist_id` и
`checklist_version` соответствующей оценки. Активная версия используется только
для признака `outdated`; она не заменяет исторический чек-лист при подсчёте.
В `appeals` возвращаются апелляции оценки; `final_results` учитывают решения,
а `original_totals` сохраняют доступ к исходному итогу. Счётчики апелляций списка
относятся к последней оценке диалога.

## Python-тесты интегратора и PowerShell

Тесты запускаются из `backend`. Вместе с ним нужны соседние папки
`test/fixtures`, `checklists` и `prompts`, уже перенесённые из архива.
Следующие команды выполняйте из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:PYTHONUTF8 = "1"
$projectPython = (Resolve-Path .\.venv\Scripts\python.exe).Path
Push-Location .\backend
try {
    & $projectPython -m pytest -q
} finally {
    Pop-Location
}
```

`PYTHONUTF8=1` включает чтение UTF-8 вместо системной CP1251 в Windows.
Активация виртуального окружения и изменение ExecutionPolicy не требуются.

с `PYTHONUTF8=1`, импорт `evaluate` успешен, `GET /health` вернул `200` и `{"status":"ok"}`.
